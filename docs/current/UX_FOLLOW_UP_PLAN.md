# PaykiTodo 体验审计与后续优化方案

## 文档目的

本文件记录 `1.15.16` 回合对 PaykiTodo 手机端、电脑端和提醒链路的用户体验审计结果。提醒状态与通知入口中的部分 P0 项已在 `1.15.17` 实现；更新后的日历待办方案和扩展审计见 `CALENDAR_TODO_AND_UX_REVIEW_PLAN.md`。

## 本轮已修复的体验问题

1. 电脑端品牌图标不一致：登录页和工作台现在复用手机端维护中的 launcher artwork。
2. 电脑端待办层级冗余：移除无操作价值的加载统计和“待办主时间轴”，只保留“待办”和“历史待办”两段，并保留分组筛选、搜索和分页。
3. 电脑端周视图边界不稳定：周视图现在只接受周一至周日或周日至周六，且设置与手机端同步。
4. 进行中日程通知耗电：移除系统 chronometer，通知只显示原定时间段。
5. 未来待办提醒选择困难：新增“我知道了”，只关闭本次提醒，不修改任务状态和 DDL；全屏 Activity 与无障碍浮层保持一致。
6. 同步地址发现成本高：服务运行且发现可访问地址后直接展示 URL，取消手动显示/隐藏按钮。

## 待审核问题清单

### P0：提醒链路的状态表达仍不完全统一

复现路径：创建一个未来 DDL 待办并设置提醒，分别从全屏页面、通知栏点击进入页面、无障碍浮层处理。

现状风险：三个入口虽然已经有相同的完成、延后、知道了语义，而且“知道了”会保留同一待办尚未到点的其他提醒，但用户仍可能不清楚下一次提醒是否还会出现；循环任务、多个提醒时间和闹钟模式的组合也需要明确说明。

建议：

- 在按钮附近显示一次性结果反馈，例如“本次提醒已关闭，任务仍保留在计划中”。
- 对循环任务显示下一次提醒时间，不显示内部 ID 或调度细节。
- 把“延后”定义为改变本次提醒时间，把“知道了”定义为只关闭本次提醒，文案与行为始终保持一一对应。
- 对闹钟模式增加独立的“停止本次响铃”语义，避免用户误以为任务已经完成。

验证：覆盖锁屏、解锁、通知点击、无障碍浮层、普通通知、循环任务和多个提醒偏移；确认数据库状态、下一次 Alarm、通知和前台服务状态均符合预期。

### P1：日程和待办的操作权限仍容易混淆

复现路径：打开日程预览、待办预览、历史记录和循环任务编辑页，对比完成、取消、删除、复制按钮。

现状风险：日程不能完成，只能发生或取消；待办可以完成或取消；删除又不等同于取消。若按钮排序、颜色或文案不一致，用户会把取消当成删除，或者期待日程出现“完成”。

建议：

- 日程只显示“编辑、创建副本、取消、删除”，不显示完成。
- 待办只显示“完成、编辑、取消、删除”；取消进入历史，删除不进入历史。
- 循环项目在执行取消/删除前明确当前、当前及以后、全部三个范围，并在确认文案中写出影响。
- 统一预览底部操作区的顺序、按钮形状和危险色，避免同一职责出现多个入口。

验证：单次待办、单次日程、循环待办、循环日程分别执行四类操作，检查历史记录、后续实例、提醒调度和恢复入口。

### P1：电脑端与手机端字段一致性需要持续守护

复现路径：在手机端创建包含地点、备注、提醒渠道、多个提醒、循环规则、签到、颜色和倒数日的事项，再从电脑端编辑并保存。

现状风险：电脑端曾出现描述写入备注、地点缺失、循环字段缺失等映射不一致。新增字段如果只修改一端，后续同步会丢数据。

建议：

- 维护一份字段契约表，逐项列出数据字段、手机控件、电脑控件、JSON 名称、默认值和空值语义。
- 每增加一个编辑字段，必须同时补充 Desktop Sync round-trip 测试：手机数据 -> 网页显示 -> 网页保存 -> 手机数据。
- 对空字符串、空数组、未启用提醒和未设置 DDL 使用固定序列化约定，不能依赖前端缺省值猜测。

验证：建立包含所有非默认字段的基准事项，保存前后比较导出的 JSON 字段和值，不只比较标题。

### P1：日历视图需要更强的当前上下文

复现路径：切换日、周、月，改变周起始日，点击迷你月历今日，再左右翻页。

现状风险：当前日期、选中日期、已过去日期和当前时间线的视觉层级较多；在日视图和跨月周视图中，用户可能看不出“正在看哪一段”。

建议：

- 选中日期使用稳定的浅色圆形背景，今日使用独立蓝色强调，过去日期统一降低饱和度。
- 周视图标题明确显示完整起止日期，切换周起始日后立即重算并保留用户选中的日期。
- 当前时间线只出现在今天列；无日程时保持时间轴结构，不显示空白大卡片。
- 手机和电脑端共用同一套时间范围与“已结束日程淡出”语义。

验证：覆盖月末、跨年、周日/周一切换、无日程日、全天日程、多日程和已结束日程。

### P2：大量数据下的滚动与加载仍需量化

复现路径：导入 100、500、1000 条待办和日程，在手机待办、每日看板、日历以及电脑端分页列表中快速滚动。

现状风险：手机端已经针对 Todo 和 Calendar 做过局部重组优化，但数据量增长后，Room 查询、分组解析、卡片测量和日历事件布局仍可能成为瓶颈。

建议：

- 所有列表查询在 IO 调度器完成，UI 只接收分页/窗口化结果。
- 对分组颜色、格式化时间和重复规则文本做按 ID 或字段版本缓存。
- 日历只对可见日期窗口做事件分段，拖动过程中不重复执行全量布局。
- 对桌面端待办继续采用分页，搜索输入使用 debounce，避免每个字符请求手机。
- 建立固定数据集和帧时间基线，记录 p50、p90、p95、p99，而不是只凭主观“卡”。

验证：Pixel_8 和一台真实手机各跑一套同样数据，区分首屏、快速滚动、切换日期、打开预览四类指标。

### P2：权限失败时的解释和恢复路径不够主动

复现路径：关闭通知、精确闹钟、全屏意图、无障碍或电池优化豁免权限，再创建提醒。

现状风险：用户可能只看到“提醒没弹出来”，但不知道是哪个权限阻断，也不知道普通通知、全屏和无障碍之间的降级关系。

建议：

- 在保存提醒时显示最终有效渠道和缺失权限，而不是只在设置诊断页展示。
- 提醒触发后若全屏失败，通知内容中说明“全屏权限未开启，点击通知查看”，并给出设置入口。
- 将权限状态分为“可用、受系统限制、未授权、设备不支持”，避免只显示一个布尔值。
- 在提醒诊断中展示最近一次链路失败阶段和用户可执行的恢复动作。

验证：逐项关闭权限并触发测试提醒，确认不会静默丢失，并且用户能从当前页面完成恢复。

### P2：规划台需要继续保持“自然输入优先”

复现路径：输入只有标题、带 DDL 的自然句子、时间段、地点、备注、跨日范围和多行混合内容，分别走本地识别和 AI 识别。

现状风险：规划台已经移除旧标签主路径，但识别结果仍可能让用户疑惑“哪部分是标题、地点、备注”，AI 失败时也需要明确知道本地规则接管了。

建议：

- 预览卡片按“标题、时间、地点、备注、提醒、重复”固定顺序展示，空字段不占位。
- 识别结果必须保留原文标点和原始备注，不要为了标准化而修改用户正文。
- AI 输出必须先经过统一结构化校验，无法确定的字段保留为空并标记待确认，不要猜分组或自动生成备注。
- 本地规则作为稳定兜底，界面明确显示“AI 识别 / 本地识别”来源，但不把内部解析器术语暴露成用户负担。

验证：建立自然输入回归集，至少覆盖中文全角标点、带引号地点、日期范围、无 DDL 任务、备注和重复规则。

## 实施顺序建议

1. 先完成 P0 提醒状态统一和循环任务验证。
2. 再建立手机/电脑字段契约与 round-trip 测试，减少跨端回归。
3. 然后量化大数据量滚动和日历切换性能，基于数据决定是否需要更深层重构。
4. 最后处理权限解释和规划台识别结果的细节体验。

## 本轮边界

本文件中的其余待审核项仍作为后续产品与开发输入。下一轮开始前应先由用户确认优先级和交互文案，再拆成可验证的小回合。
