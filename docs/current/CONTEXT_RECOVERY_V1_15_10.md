## 会话错位原因

本机存在多个文件名不同、但共享同一线程 UUID `019d4e16-8f61-78e3-9028-1dccf67f1661` 的 rollout：

- `sessions/2026/04/02/rollout-2026-04-02T20-06-34-...jsonl`
- `sessions/2026/06/16/rollout-2026-06-16T17-19-59-...jsonl`
- `sessions/2026/06/16/rollout-2026-06-16T17-32-52-...jsonl`

其中：

- `17-32-52` 文件包含 1.15.8、1.15.9 和 1.15.10 的开发过程及 1.15.10 最终交付记录。
- 当前状态数据库的 `threads.rollout_path` 指向 `17-19-59`，该文件仍是当前活跃会话正在续写的文件，不能直接替换或删除。
- `session_index.jsonl` 对该 UUID 的 `updated_at` 仍停在 2026-05-16，明显早于 1.15.8–1.15.10 的实际开发时间。
- 2026-08-27 注入的 compacted 摘要停在 1.15.7，因此当前对话一开始错误地看到了旧版本基线。

这是 Codex 会话索引/rollout 关联错位，不是 PaykiTodo Git 历史丢失，也不是项目文件回退。原始 rollout 和状态文件均保留，不在项目修复中删除它们。

## 后续恢复规则

1. 先以 `app/build.gradle.kts`、`git log` 和 `docs/current/PROJECT_STATUS.md` 判断版本，不以聊天摘要判断版本。
2. 再读取 `CURRENT_TASK.md`、`SESSION_HANDOFF.md`、`FEATURE_LEDGER.md` 和本文件。
3. 同一 UUID 出现多个 rollout 时，使用包含最新已完成版本交付记录的 rollout 作历史证据；不要把它强行替换成当前仍在写入的 active rollout。
4. 不直接拼接或改写正在使用的 Codex JSONL，不直接修改 `state_5.sqlite` 的 active rollout 指针，除非用户明确要求并且已完成独立备份与状态迁移验证。
5. 后续会话结束前，必须把最新版本、完成内容、未完成事项和验证证据写入 `docs/current/SESSION_HANDOFF.md`。
