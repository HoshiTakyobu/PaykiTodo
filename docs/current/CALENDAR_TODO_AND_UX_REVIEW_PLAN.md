# 日历待办展示与整体体验优化审核方案

## 文档状态

- 适用基线：`1.15.17` 开发回合。
- 本文只定义待审核的产品方案，不代表相关建议已经全部实现。
- 本轮已经落实的代码修改：电脑端日程编辑预览时间轴修正；提醒入口改为全屏/通知栏独立多选；提醒完成、延后、确认后的通知行为按所选渠道统一。

## 一、日历中显示待办的推荐方案

### 1. 设计目标

日历需要同时回答两个不同问题：

1. 日程：某个时间段会发生什么，占用多久。
2. 待办：某件事需要在什么时候之前完成，但通常没有明确持续时长。

因此，待办不能直接复用日程矩形块。否则一个 `18:00` 截止的待办会被错误表达成从某个时间开始、持续一段时间的活动，用户也会误以为拖动块是在修改日程时间段。

### 2. 总体交互

- 日历工具栏增加“显示待办”开关，手机端和电脑端分别记住用户选择。
- 推荐默认开启，只显示未完成、未取消的待办。
- 提供二级筛选：`全部待办 / 仅有 DDL / 隐藏已完成`。首版只需要“显示待办”和“显示已完成”两个开关。
- 点击待办打开待办预览；点击日程打开日程预览，两个对象的操作语义不混用。
- 待办可直接勾选完成；日程不显示完成勾选框。
- 待办颜色沿用主分组颜色，日程颜色沿用日程颜色或日程分组颜色。

### 3. 日视图

#### 无精确时间的待办

- 在全天日程区域下方增加紧凑的“待办”横向区域，不放进小时网格。
- 无 DDL 待办按现有产品语义归入今日，在这里显示。
- 只有日期、没有具体时刻的待办也放在这里。
- 单项结构：完成圆框、标题、分组色标；不显示虚假的开始和结束时间。
- 超过三项时折叠为“还有 N 项”，点击展开，不无限挤压时间轴。

#### 有精确 DDL 的待办

- 在对应时刻显示一个短横线或菱形里程碑标记，并在右侧显示标题。
- 标记只表达截止时刻，不拉伸成具有高度的日程块。
- 与日程重叠时，待办标记放在时间轴边缘，不覆盖日程正文。
- 已逾期未完成使用错误色描边，不使用整块高饱和红色背景。

### 4. 周视图

- 每日列顶部保留一个最多两行的待办区，用于无精确时间的待办。
- 有精确 DDL 的待办在对应日期列、对应时刻显示里程碑标记。
- 同一小时待办过多时聚合为“3 项待办”，点击后弹出该时刻的列表。
- 周视图首版不支持拖动待办，避免误操作和移动范围不明确。

### 5. 月视图

- 月视图不塞入完整待办卡片，避免日期格高度失控。
- 每个日期格最多显示两条紧凑标题，日程和待办使用不同图形：日程为短色条，待办为小圆框或勾选图标。
- 超出数量显示 `+N`，点击日期进入日视图或当天事项列表。
- 已完成待办默认不占月视图空间；用户开启“显示已完成”后，以低透明度显示。

### 6. 编辑与拖动边界

- 点击待办标记进入待办预览，不直接进入全屏编辑器。
- 待办勾选只改变完成状态，不修改 DDL、提醒或循环规则。
- 后续若增加拖动：拖动待办只修改 DDL；绝不自动生成日程开始时间、结束时间或同步日程。
- 循环待办拖动前必须询问“仅当前 / 当前及以后 / 全部”，并预览受影响日期。
- 无 DDL 待办从顶部待办区拖入时间轴属于高风险语义转换，首阶段不实现。

### 7. 数据与性能约束

- Room 查询按当前可见日、周或月窗口读取待办，不把全部历史待办交给日历布局。
- UI 层使用稳定 ID，日期格式、分组颜色和布局结果按事项版本缓存。
- 月视图只计算数量和前两条摘要；进入日视图后再加载完整事项。
- 首阶段性能验收数据集：100、500、1000 条活动事项，记录首屏、切日、切周、快速滚动的 p50、p90、p95、p99 帧时间。

### 8. 推荐实施顺序

1. 第一阶段：日视图和周视图只读展示、打开预览、勾选完成。
2. 第二阶段：月视图摘要、显示待办开关、显示已完成开关。
3. 第三阶段：同一时刻聚合、循环范围处理、无障碍与键盘操作。
4. 第四阶段：在性能基线达标后，再评估拖动修改 DDL。

### 9. 建议审核结论

建议批准第一、二阶段，暂不批准拖动功能。原因是查看、完成和打开预览已经覆盖主要需求，而拖动会同时影响 DDL、提醒、循环范围和误操作恢复，开发与回归成本明显更高。

## 二、整体体验问题补充审计

### P0：按钮文案与数据修改必须严格一致

已发现的典型问题是“延后10分钟提醒”曾在 DDL 已过期或早于新提醒时间时自动推迟 DDL。用户只授权修改提醒，程序却修改了任务约束。

优化原则：

- “延后提醒”只修改提醒时间。
- “推迟 DDL”必须是独立操作，并明确显示新旧 DDL。
- “我知道了”只关闭本次已触发提醒，不完成、不取消、不修改 DDL。
- 所有隐式联动必须在保存前展示，不能靠提交后的提示解释。

本轮状态：提醒延后不再修改 DDL；延后期间不会因旧 DDL 已过而被提前标记为错过。

### P0：通知点击必须进入用户预期页面

现状风险：全屏提醒处理后若保留通知，点击通知再次进入全屏提醒页，会迫使用户重复处理同一提醒。

优化原则：

- 未处理的提醒通知可以进入提醒页。
- “延后10分钟提醒”或“我知道了”后的保留通知进入事项预览。
- “我已完成”后通知立即消失。
- 保留通知必须静默、可划走、点击后自动消失，不再携带 full-screen intent。

本轮状态：上述行为已在全屏 Activity 和无障碍兜底浮层中统一。

### P0：取消、删除、完成的结果必须可预测

- 完成待办：进入历史，状态为已完成。
- 取消待办：进入历史，状态为已取消。
- 取消日程：进入历史，状态为已取消。
- 删除：不进入历史，数据被移除。
- 日程不存在“完成日程”。
- 循环事项的取消和删除必须询问作用范围，并在确认页列出受影响实例数量或日期范围。

建议增加短时撤销入口：取消或删除后在底部显示 5 秒 Snackbar。删除的撤销需要软删除或短时缓存，必须单独设计数据安全策略。

### P1：编辑页的保存与返回规则需要全局一致

目标规则：只有点击右上角“完成”才保存；系统返回、左上角返回、下滑关闭和点击遮罩都直接放弃本次草稿，不弹“放弃编辑”确认。

需要逐页审计：

- 待办创建与编辑。
- 日程创建与编辑。
- AI 源配置与日报/周报设置。
- 分组创建与编辑。
- 规划台候选编辑。
- 提醒、循环和签到设置子页面。

风险点：编辑已有事项时，直接返回放弃可能让用户误以为自动保存。建议在标题栏固定展示“完成”，并避免页面内再次出现“保存”按钮；但不新增阻塞确认框。

### P1：手机端与电脑端字段必须由契约约束

每个事项字段应维护一份跨端契约：字段名、类型、空值语义、手机控件、电脑控件、API JSON 名称、默认值和保存策略。

必须覆盖：

- 标题换行、备注、地点。
- 多分组与主分组。
- DDL、日程开始/结束、全天。
- 全屏/通知栏提醒多选、多个提醒时间、响铃、震动、闹钟模式。
- 循环规则和操作范围。
- 倒数日、签到、签到提醒、颜色。
- 日程创建副本、多时间段课程。

建议建立 round-trip 自动化测试：手机创建全字段事项，电脑读取并原样保存，再比较数据库快照，禁止未展示字段被重置。

### P1：权限失败不能只表现为“没有弹出来”

提醒保存后应展示“当前设备实际可用能力”，区分：

- 通知权限未授权。
- 精确闹钟不可用。
- 全屏意图不可用。
- 无障碍兜底未开启。
- OEM 电池策略可能限制后台启动。

建议在提醒诊断页显示最近一次失败阶段、时间和可执行操作。普通用户不需要看到内部类名或异常栈，只需要看到“哪里被系统阻止”和“去哪里打开”。

### P1：循环事项修改需要结果预览

当前、当前及以后、全部三个范围，仅靠按钮文字不足以避免误操作。

建议确认页展示：

- 当前实例日期。
- 第一条受影响的未来实例。
- 预计影响数量。
- 修改后下一次提醒时间。
- 是否会删除已生成但尚未完成的实例。

保存后给出结果摘要，例如“已更新 6 条未来待办，下一次为 9月2日 08:00”。

### P1：规划台必须解释字段来源，而不是暴露解析复杂度

- 候选卡固定按标题、时间、地点、备注、提醒、重复顺序显示。
- 标明“AI 识别”或“本地识别”，但不展示解析器内部术语。
- 猜测字段要有可见标记，尤其是分组、地点和重复规则。
- 原文标点和备注必须保留，结构化过程不能改写正文。
- AI 失败时明确说明已切换本地识别，不能静默给出质量明显不同的结果。

### P2：日历和长列表需要固定性能基线

不能只用“感觉更流畅”作为验收。建议为待办、每日看板、日历分别建立固定数据库和 Macrobenchmark：

- 首次进入页面。
- 快速上下滚动。
- 日历左右切日、切周、切月。
- 打开事项预览和返回原位置。
- 批量选择 20、100 条待办。

每次性能改动记录数据规模、设备、p50/p90/p95/p99 和慢帧比例。若 UI 功能正确但 p95 明显退化，不应直接发布。

### P2：导航与滚动上下文不能无故丢失

- 从通知或 Widget 打开事项，关闭预览后应回到合理页面，而不是统一回到每日看板顶部。
- 从日历打开日程后返回，应保留原日期、视图模式和滚动时刻。
- 从待办列表打开事项后返回，应保留分组筛选、搜索词和列表位置。
- 手机与电脑端都应对这些状态做页面级保存，不把短期交互状态写进数据库。

### P2：空状态应提供唯一、直接的下一步

空状态不应只写“暂无内容”，也不应放多个竞争按钮。

- 无待办：提供“新建待办”。
- 无日程：提供“新建日程”。
- 无倒数日：说明在待办或日程编辑中开启倒数日。
- 规划台空文档：保持占位提示，不写入实际文档内容。
- AI 报告未生成：说明生成条件和最近一次失败原因。

## 三、建议下一轮优先级

1. P0：为提醒保留通知与详情跳转补充模拟器和真机回归，覆盖完成、延后、知道了、日程确认、签到。
2. P1：建立手机/电脑全字段 round-trip 测试，先阻止静默丢字段。
3. P1：实现日历待办第一阶段，只读展示、完成、预览，不做拖动。
4. P1：循环操作确认页增加影响范围预览。
5. P2：建立 500/1000 条数据性能基线，再继续优化日历和待办列表。

## 四、需要产品审核的决策

1. 日历“显示待办”是否默认开启。本文建议默认开启。
2. 无 DDL 待办是否继续统一归入今日。本文沿用当前产品语义。
3. 月视图是否允许直接勾选完成。本文建议首版只打开当天列表，避免日期格误触。
4. 是否接受首阶段不支持拖动待办。本文建议接受。
5. 删除是否需要 5 秒撤销。若接受，需要先确定软删除或临时缓存策略。
