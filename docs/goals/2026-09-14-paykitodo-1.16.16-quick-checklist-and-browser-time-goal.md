不要只完成其中一个客户端的假 UI，也不要只把整段文本塞进一个备注字段。快速清单中的每一项任务都必须成为可独立完成、取消、删除、同步和进入历史记录的真实待办。

## 1. 需求背景与目标

### 1.1 背景

PaykiTodo 当前拥有待办、日程、规划台和管理后台，但用户在每日看板或待办页面中输入一组具有层级关系的任务时，仍然需要逐条创建任务。用户希望拥有一个类似 Typora 编辑体验的“快速待办清单”：

- 输入一行标题。
- 使用行首短横线数量表达任务层级。
- 使用回车实时生成下一行并即时预览。
- 使用 `--#` 为最近的子任务添加可见说明。
- 确认后一次性生成一个可展开/收缩的待办组。
- 每个叶子或父级任务都是真实待办，能够使用已有的完成、取消、删除、历史、Widget 和同步逻辑。

同时，管理后台目前将服务器本地时区用于格式化时间。Azure 服务器常使用 UTC，导致用户在北京时间访问时看到的注册时间、同步时间、设备活跃时间和审计日志时间整体少 8 小时。该逻辑应该改成浏览器本地时间。

### 1.2 本轮目标

本轮必须完成以下两个目标：

**目标 A：管理后台浏览器本地时间**

- 后端传递时间戳或 UTC 标准时间。
- 前端浏览器使用自身时区格式化显示。
- 浏览器位于 `Asia/Shanghai` 时显示北京时间；浏览器位于其他时区时跟随其他时区。
- 所有管理后台时间字段统一处理。

**目标 B：快速待办清单**

- 每日看板和待办页面各有一个快捷入口。
- 使用统一的编辑、解析、预览、保存和任务层级语义。
- 保存后形成可展开/收缩的待办组。
- 每个任务进入现有待办业务体系。
- 父子任务完成状态、取消/删除、历史记录、备份、同步和 Widget 行为一致。

## 3. 总体产品定义

### 3.1 快速待办清单是什么

快速待办清单是一种“待办组容器 + 层级待办任务”的组合：

- 清单有一个标题，例如 `0913待办`。
- 清单标题只是容器标题，不是一条待办，不进入历史记录。
- 清单包含一棵或多棵层级任务树。
- 每一个以短横线开头的任务行都会创建一条真实待办。
- 子任务通过 `parentId` 与父任务关联。
- 每个任务保留输入顺序，通过 `sortOrder` 排序。
- 清单可以展开或收缩。
- 清单本身不因子任务完成而进入历史记录。
- 任务完成或取消时，按照普通待办规则进入历史记录。

### 3.2 与现有 TaskGroup 的区别

不要把快速清单标题直接当成现有颜色分组或 `TaskGroup`：

- `TaskGroup` 是已有的分类、颜色或筛选概念。
- 快速清单是一个有父子层级和展开/收缩状态的容器。
- 两者可以有默认关联，但概念不能混淆。
- 快速清单标题不应被当成一个可完成任务。

### 3.3 默认行为

保存快速清单后：

- 默认归入“今日待办”逻辑。
- 默认日期为保存时的本地当前日期。
- 默认没有 DDL。
- 默认没有提醒。
- 默认不创建日程。
- 默认任务为未完成、未取消、未删除。
- 默认保存后展开新建清单。
- 默认使用现有待办的默认颜色或当前选择的默认分组，但不要让用户在这个快捷编辑器中面对大量低频配置。

如果未来要支持 DDL、提醒、颜色或分组，应该在清单确认后进入统一的待办编辑页面追加设置，而不是在本轮把快捷编辑器做成复杂表单。

## 4. 管理后台：改为浏览器本地时间

### 4.1 适用字段

以下字段必须全部使用同一套浏览器时区格式化逻辑：

- 用户注册时间。
- 用户最近同步时间。
- 用户最后活跃时间。
- 设备最后活跃时间。
- 审计日志时间。
- 后台中任何由 Unix 时间戳或服务器时间生成的时间字段。

实现完成后，不能存在一部分时间按服务器格式化、另一部分时间按浏览器格式化的混合状态。

### 4.2 后端输出契约

后端不要把已经使用 `time.localtime()` 格式化后的时间作为主要显示值传给页面。推荐输出以下结构：

```html
<time class="js-local-time" data-epoch-seconds="1789389300">
  时间加载中
</time>
```

要求：

- `data-epoch-seconds` 使用 Unix epoch 秒。
- 数据为空时使用空值，例如 `data-epoch-seconds=""`。
- 用户数据、用户名、设备名、审计内容必须经过 HTML 转义。
- 不要把用户数据拼接进 JavaScript 源码。
- 不要把真实时间戳作为 JavaScript 标识符或未转义字符串注入。
- 可以保留服务器端函数用于日志或非页面场景，但管理页面主显示不可再依赖它。

### 4.3 浏览器格式化逻辑

页面加载后使用浏览器自身时区格式化：

```javascript
const browserTimeZone = Intl.DateTimeFormat().resolvedOptions().timeZone || "未知时区";

function formatBrowserLocalTime(seconds) {
  const epochSeconds = Number(seconds);
  if (!Number.isFinite(epochSeconds) || epochSeconds <= 0) {
    return "-";
  }

  const parts = new Intl.DateTimeFormat("en-CA", {
    year: "numeric",
    month: "2-digit",
    day: "2-digit",
    hour: "2-digit",
    minute: "2-digit",
    hour12: false
  }).formatToParts(new Date(epochSeconds * 1000));

  const values = Object.fromEntries(parts.map(({ type, value }) => [type, value]));
  return `${values.year}-${values.month}-${values.day} ${values.hour}:${values.minute}`;
}

document.querySelectorAll(".js-local-time").forEach((element) => {
  element.textContent = formatBrowserLocalTime(element.dataset.epochSeconds);
});

const timeZoneElement = document.querySelector("[data-browser-time-zone]");
if (timeZoneElement) {
  timeZoneElement.textContent = `浏览器时区：${browserTimeZone}`;
}
```

实现 Agent 可以调整代码结构，但必须保持以下行为：

- `new Date(epochSeconds * 1000)` 作为时间点来源。
- 不传 `timeZone`，从而跟随浏览器本地时区。
- 北京浏览器显示北京时间，其他时区跟随其他时区。
- 格式至少包含年、月、日、小时、分钟。
- 分钟和月份使用两位数。
- 空值显示 `-`。

### 4.4 JavaScript 禁用时的降级

JavaScript 禁用时不能把服务端 UTC 时间伪装成北京时间。可选方案：

1. 显示明确的 UTC ISO 文本，例如 `UTC 2026-09-14T12:35:00Z`。
2. 或显示“请启用 JavaScript 以按浏览器时区显示”。

降级内容必须可读，并且不能让用户误以为那是北京时间。

### 4.5 后台时间验收

至少通过以下测试：

1. 将测试环境服务器时区设为 UTC，页面仍能正常渲染。
2. 模拟浏览器时区 `Asia/Shanghai`，epoch 时间显示为北京时间。
3. 模拟浏览器位于 `America/New_York`，时间跟随纽约时区，而不是固定加 8 小时。
4. 用户注册、最近同步、设备活跃、审计日志全部使用同一套脚本。
5. 页面自动刷新后仍使用浏览器本地时间。
6. 时间字段为空时显示 `-`。
7. 用户名、设备名、审计文本包含 HTML 特殊字符时不能造成 XSS。
8. HTML 中存在 `data-epoch-seconds`，且页面包含本地时间格式化逻辑。

## 5. 快速待办清单入口与页面结构

### 5.1 入口位置

必须有两个入口：

- 每日看板页面一个。
- 待办页面一个。

两个入口必须调用同一个业务入口和同一套编辑器，不允许 Android 和 Web 各写一套不同解析规则。

入口按钮要求：

- 采用图标按钮，不使用长文字按钮。
- 图标语义为“感叹号 + 上下翻动的作业本”。
- 优先组合项目已经使用的 Material/Lucide 图标，或使用现有资源。
- 不要手写复杂 SVG。
- `contentDescription`/`aria-label` 使用 `快速清单`。
- 提供 tooltip 或无障碍名称。
- 不能遮挡每日看板现有的新增待办、创建日程、筛选和导航控件。
- 窄屏下不能溢出、挤压或覆盖其他按钮。

如果现有设计系统没有“感叹号 + 作业本”的单个图标，可以使用两个已有图标叠放或一个项目现有的相近图标，但必须保持两个入口视觉一致。

### 5.2 编辑/预览窗口

这是一个编辑和预览窗口，不是直接写库的输入框。

手机端：

- 使用全屏或接近全屏的编辑页面/BottomSheet。
- 顶部显示返回/关闭、标题和确定按钮。
- 输入区和预览区必须有明确层次。
- 小屏不能出现横向滚动或按钮出界。
- 键盘打开后，输入框和当前预览仍然可操作。

桌面 Web/Windows：

- 使用足够宽的编辑界面。
- 推荐左右分栏：左侧编辑、右侧实时预览。
- 分栏在窄窗口下可以改为上下排列。
- 预览区域不可被顶部操作栏遮挡。

公共行为：

- 输入内容实时解析并更新预览。
- 每次按 Enter 后，新行立即出现，并按照上一行层级生成默认前缀。
- 点击取消、返回、关闭或系统返回时，不写入数据库。
- 点击确定时再次完整解析，不能只相信预览缓存。
- 存在解析错误时禁止保存，并定位到对应输入行。
- 保存成功后关闭编辑页，并在每日看板/待办页面展开新建清单。

### 5.3 界面文案

建议使用以下明确文案：

- 入口无障碍名：`快速清单`
- 页面标题：`快速待办清单`
- 保存按钮：`确定`
- 取消按钮：`取消`
- 解析错误：`第 N 行：具体错误原因`
- 保存成功：`已创建清单：清单标题`
- 预览摘要：`N 项任务 · M 层 · K 条说明`

不要把“Markdown 兼容编辑”“规划文档”等内部实现术语强塞给普通用户。用户看到的是快速待办清单，而不是数据库或解析器名称。

## 6. 输入语法规范

### 6.1 完整示例

```text
0913待办 //标题行
- 准备浙大的资料
-- 1. 身份证复印件
-- 2. 个人简历
-- 3. 成绩排名
--# 成绩排名是本学年的
- 取快递（取件码114514）
```

解析结果应为：

- 清单标题：`0913待办`
- 一级任务：`准备浙大的资料`
  - 二级任务：`1. 身份证复印件`
  - 二级任务：`2. 个人简历`
  - 二级任务：`3. 成绩排名`
    - 说明：`成绩排名是本学年的`
- 一级任务：`取快递（取件码114514）`

### 6.2 隐藏行内注释 `//`

规则：

- 一行中第一个 `//` 及其右侧内容都是编辑注释。
- 注释不属于真实标题、任务标题或备注。
- 注释不进入预览。
- 注释不进入数据库。
- 去除注释后为空的行忽略。
- 首版不支持 `//` 转义；遇到第一个 `//` 即开始注释。
- 实现 Agent 必须在编辑器附近显示简短占位提示，告诉用户 `//` 后内容不会保存，避免用户误以为它是任务文本。

因此：

```text
0913待办 //标题行
```

实际标题是：

```text
0913待办
```

### 6.3 标题规则

- 第一条去掉空白和 `//` 注释后仍有内容的非空行，是清单标题。
- 标题行不要求以短横线开头。
- 标题行不创建 TodoItem。
- 标题前的空行和纯注释行忽略。
- 如果没有有效标题，禁止保存并提示“请先输入清单标题”。
- 如果第一条有效内容是任务行，应提示标题缺失，而不是把任务内容静默当作标题。

### 6.4 任务层级

以行首连续短横线数量表示层级：

- `-`：一级任务。
- `--`：二级任务。
- `---`：三级任务。
- 以此类推。

短横线后的正文全部保留，包括数字序号：

```text
-- 1. 身份证复印件
```

任务正文是：

```text
1. 身份证复印件
```

`1.` 不是层级标记，不能被解析器删除，也不能影响父子关系。

短横线与正文之间允许零个或多个空格，但保存后建议统一为一个显示空格。任务正文去除首尾空白；正文为空时提示该行没有任务内容并禁止保存，除非它是用户刚按 Enter 产生的尚未填写行，且该行在最终保存时应被忽略或提示用户。

### 6.5 可见说明行 `--#`

说明行格式：

```text
--# 成绩排名是本学年的
```

规则：

- `--#` 前的短横线数量表示说明所在层级。
- `#` 只在紧跟短横线之后代表说明标记。
- 说明行不是可勾选任务。
- 说明文字必须正常显示在预览中。
- 说明文字建议保存到对应 TodoItem 的 `notes`/备注字段。
- 多条说明按输入顺序合并，并以换行保留。
- 说明不创建额外 TodoItem。
- 说明之前没有可关联任务时，不能静默丢弃，必须显示错误或未关联警告。
- 首选关联最近的同级任务；如果同级没有任务，关联最近的上级任务。
- 说明不应错误地关联到后续任务。

例如：

```text
-- 3. 成绩排名
--# 成绩排名是本学年的
```

说明属于 `3. 成绩排名`。

### 6.6 空行、普通行和非法行

- 空行忽略。
- 纯 `//` 注释行忽略。
- 标题之后，既不是任务行，也不是说明行的普通文本，首版不能偷偷创建普通任务。
- 普通文本应在预览中显示为格式错误，并给出行号。
- 非法层级、空任务、孤立说明、缺少标题均必须阻止最终保存。
- 解析错误要能定位原始行号。

### 6.7 层级跳跃

推荐解析策略：

- 使用 `lastNodeByDepth` 或栈保存最近任务。
- 新任务的父节点是最近一个深度小于当前深度的任务。
- 同级任务挂在同一个父节点下，并按照原始顺序排序。
- 如果用户从 `-` 直接跳到 `---`，允许挂到最近的一级任务，但预览中显示层级跳跃警告。
- 如果没有任何更浅层任务可作为父节点，显示错误并禁止保存。

实现 Agent 不得因用户没有写序号而解析失败。

## 7. 解析器设计

### 7.1 分阶段处理

解析器应拆成可测试的纯函数，不要把文本分割、UI 状态更新、数据库写入混在一个点击回调中。

推荐流程：

1. 保留原始文本和原始行号。
2. 按行去除 `//` 后的隐藏注释。
3. 忽略空行，找出第一条有效标题。
4. 解析标题之后的任务和说明。
5. 建立父子关系和同级排序。
6. 生成诊断信息：错误、警告、任务数量、最大深度、说明数量。
7. 生成 UI 预览模型。
8. 点击确定时重新执行 1-7。
9. 无错误时转换为事务写入模型。

### 7.2 推荐中间模型

名称可根据代码风格调整，但语义应保持一致：

```text
QuickChecklistDraft
  title: String
  nodes: List<QuickChecklistDraftNode>
  diagnostics: List<ParseDiagnostic>
  taskCount: Int
  maxDepth: Int
  noteCount: Int

QuickChecklistDraftNode
  temporaryId: String
  parentTemporaryId: String?
  depth: Int
  title: String
  notes: String?
  sourceLine: Int
  sortOrder: Int
  kind: TASK

ParseDiagnostic
  severity: ERROR | WARNING
  sourceLine: Int
  message: String
```

### 7.3 伪代码

以下伪代码表达行为契约，实际语言可以是 Kotlin、TypeScript 或 Python：

```text
parseQuickChecklist(rawText):
    lines = splitPreservingLineNumbers(rawText)
    visibleLines = []

    for line in lines:
        withoutComment = line.substringBeforeFirst("//")
        if trim(withoutComment) is not empty:
            visibleLines.add(line.number, withoutComment)

    titleLine = first visible line that is not a task or note line
    if titleLine is missing:
        return error("缺少清单标题")

    title = trim(titleLine.content)
    stack = empty map depth -> last task
    lastTaskByDepth = empty map
    nodes = []

    for line after titleLine:
        if matches note pattern ^(-+)#\s*(.*)$:
            depth = length(capture 1)
            noteText = trim(capture 2)
            target = lastTaskByDepth[depth]
                     or nearest previous task with depth < depth
            if target is missing:
                add ERROR at line.number
            else:
                append noteText to target.notes
            continue

        if matches task pattern ^(-+)\s*(.*)$:
            depth = length(capture 1)
            title = trim(capture 2)
            if title is empty:
                add ERROR at line.number
                continue

            parent = nearest previous task with depth < depth
            if depth > 1 and parent is missing:
                add ERROR at line.number
                continue
            if depth > 1 and parent.depth != depth - 1:
                add WARNING for a level jump

            node = create task node with source line and sort order
            node.parent = parent
            nodes.add(node)
            lastTaskByDepth[depth] = node
            remove stale entries deeper than depth
            continue

        add ERROR: unsupported line after title

    return draft(title, nodes, diagnostics)
```

若采用“允许层级跳跃”的策略，解析器应在预览中明确显示警告；若项目实现选择严格禁止跳跃，也必须在文档和错误提示中保持一致。推荐允许并警告，因为用户输入应尽可能不丢数据。

### 7.4 去重与重复导入

同一段文本被用户重复点击确认，或同一备份被重复导入时，不得无提示地产生重复清单。

推荐：

- 保存前生成稳定的内容指纹：标题、任务标题、层级、顺序、说明的规范化组合。
- 指纹不能只使用标题，因为同名清单可以合法存在。
- 数据库保存 `sourceFingerprint` 和 `createdAt`。
- 对明确相同的未修改草稿，在相同设备上重复提交时提示已存在并阻止重复创建。
- 云端同步以稳定 ID 和版本号为主，不能仅靠标题去重。
- 若用户确实想再次创建相同内容，可在标题或内容上做实际修改后再保存。

## 8. Enter 与编辑器交互

### 8.1 默认插入规则

按 Enter 后默认复制上一条任务行的短横线层级：

```text
- 一级任务
```

按 Enter 后：

```text
-
```

```text
-- 二级任务
```

按 Enter 后：

```text
--
```

如果上一行是说明行：

```text
--# 说明
```

下一行默认应回到：

```text
--
```

不能继续自动生成 `--#`，否则用户会被迫连续输入说明。

### 8.2 光标与 IME

Android 的软键盘 Enter 可能通过 IME 事件而不是普通键盘事件到达，必须确认：

- 不会重复插入两个换行。
- 光标落在新行正文之后。
- 自动前缀不会破坏用户已经输入的内容。
- 用户手动删除或增加短横线后，下一次 Enter 使用当前上一行的真实层级。
- Web 的 `keydown`、移动端输入法和粘贴多行文本都使用同一解析器。
- 粘贴多行文本后，逐行即时解析，不要求用户重新输入。

### 8.3 预览更新

- 文本变化后以防抖方式或轻量方式更新预览。
- 每次 Enter 后必须立即更新。
- 解析失败时，已经能识别的内容仍可预览，但错误行必须高亮或列出。
- 预览不能因为单行错误而显示成空白页面。

## 9. 预览视觉与行为规范

预览应接近电脑版 Typora 的任务列表渲染效果：

```text
□ 准备浙大的资料
    □ 1. 身份证复印件
    □ 2. 个人简历
    □ 3. 成绩排名
        成绩排名是本学年的
□ 取快递（取件码114514）
```

要求：

- 所有任务行显示勾选框。
- 子任务按深度缩进。
- 说明行不显示勾选框，显示为普通说明文本。
- 数字序号保留。
- 说明文字可换行但不得被截断。
- 预览中的勾选框可以只读；如果允许直接勾选，必须明确它是待保存草稿。
- 预览中的状态修改不能绕过最终事务保存。
- 显示任务数、最大深度和说明数摘要。
- 显示错误行号和错误原因。
- 不要用大量嵌套卡片包裹每个节点；保持与现有待办卡片一致。

## 10. 数据模型与数据库方案

### 10.1 推荐架构

推荐“独立清单容器 + 复用正式 TodoItem”的方案：

```text
QuickChecklistGroup
  id
  title
  collapsed
  sourceFingerprint
  createdAt
  updatedAt
  archivedAt nullable

TodoItem（已有模型扩展可选字段）
  quickChecklistGroupId nullable
  parentTodoId nullable
  quickChecklistDepth nullable
  quickChecklistSortOrder nullable
  origin = QUICK_CHECKLIST 或等价枚举
  notes（复用已有备注字段）
```

核心原则：

- 清单组不是 TodoItem。
- 清单中的每个任务都是正式 TodoItem。
- `TodoItem` 的完成、取消、删除状态是任务状态唯一来源。
- 父子关系和排序保存在清单关系字段中。
- 不要仅把全文保存在一个备注字段。
- 不要让一个任务同时被错误地写入多个清单组。

如果现有 `TodoItem` 不适合扩展，可以新增 `QuickChecklistItem`，但它必须拥有稳定的 `linkedTodoId`，并且所有用户可见的完成、取消、删除操作最终调用现有 TodoRepository 的正式待办路径。不能创建“看起来像待办、实际上不在历史和同步里的影子任务”。

### 10.2 是否复用 PlanningNode

实现 Agent 必须先阅读 `PlanningNode` 的完整使用范围。

推荐判断：

- 如果给 `PlanningNode` 增加清单来源、脱离 `PlanningNote` 日期、独立清单组 ID 后，不会污染规划台历史语义，可以复用其父子遍历和祖先完成计算代码。
- 如果复用会导致快速清单被错误绑定到当前规划文档，或被规划文档日期过滤，使用独立 `QuickChecklistGroup/QuickChecklistItem`。
- 无论采用哪种方案，都应该抽取或复用一个公共的树状态服务，避免 Android、Web、Windows 各自实现父任务完成逻辑。

本需求最重要的不是表名，而是以下外部行为必须一致：层级不丢失、任务是正式待办、完成/取消进历史、同步后结构一致。

### 10.3 Room migration

若需要新增表或字段：

- 当前数据库版本若为 30，新增 migration `30 -> 31`。
- 更新 `AppDatabase.version`。
- 导出 Room schema。
- 增加 migration 测试。
- 旧数据库升级后已有待办、日程、规划文档、历史记录不能丢失。
- 旧数据的清单字段使用空值兼容。
- 不要在 migration 中把已有普通待办误判为快速清单任务。

若实际基线数据库版本不同，以代码为准，但必须遵守单向可升级、可测试、不可丢数据的原则。

## 11. 保存事务与业务语义

### 11.1 保存流程

点击“确定”后必须执行：

1. 再次解析全文。
2. 有错误则阻止保存，并定位第一处错误。
3. 创建清单组容器。
4. 按原始顺序创建所有正式 TodoItem。
5. 保存每个任务的父子关系、深度和排序。
6. 将说明写入对应任务的备注字段。
7. 设置默认日期为保存时本地今日。
8. 设置无 DDL、无提醒、未完成状态。
9. 写入稳定内容指纹。
10. 在同一数据库事务中完成全部操作。
11. 任一任务创建失败时回滚整个清单，不能留下半个清单。
12. 提交后刷新所有受影响的本地和远程观察者。

### 11.2 完成

- 勾选任务等同于完成一条普通待办。
- 完成必须走现有 Repository/业务服务，不允许只改 UI 勾选状态。
- 所有直接子任务完成后，父任务自动标记为完成。
- 多级父任务要递归向上计算。
- 父任务自动完成时，历史记录、Widget 和云端同步状态必须一致。
- 如果父任务存在被取消但未完成的子任务，不能把它们伪装成已完成。
- 推荐规则：只有全部子任务均为“已完成”时自动完成父任务；被取消的子任务不计入完成条件。
- 父任务直接完成时，可以沿用现有规划节点行为联动子树；必须在实现文档中明确，并保持所有端一致。

### 11.3 取消/归档

- 取消不是删除。
- 取消的任务进入已有历史记录，状态为“已取消”。
- 取消必须调用统一的取消/归档业务路径。
- 取消任务不能再出现在未完成待办列表，但可以在清单历史语义允许的范围内显示状态。
- 取消一个父任务时，推荐询问并取消整棵子树，确认文案必须说明范围；不要让父任务已取消而子任务仍显示为正常可操作但无归属。
- 若业务决定只取消父任务，也必须保证子任务状态和 UI 语义不矛盾；推荐整棵子树一致取消。
- 快速清单组本身不写入待办历史；历史只记录实际 TodoItem。

### 11.4 删除

- 删除不同于取消。
- 删除不进入历史记录。
- 删除单个任务时必须重新计算祖先状态。
- 删除父任务时应明确是否删除整棵子树；推荐沿用现有待办树删除确认策略并默认整棵子树处理。
- 删除后不能留下孤儿 `parentId` 或无法展开的清单节点。

## 12. 每日看板行为

### 12.1 入口

- 每日看板放置快速清单图标按钮。
- 入口可以靠近“今日待办”标题或顶部操作栏。
- 不能与新增待办、创建日程、设置、同步状态重叠。
- 保存成功后的清单显示在今日待办区域。

### 12.2 清单展示

清单容器显示：

- 清单标题。
- 已完成数量/总任务数量。
- 展开/收缩图标按钮。
- 必要的状态摘要。

行为：

- 新建后默认展开。
- 点击无文字图标切换展开/收缩。
- 子任务按深度缩进。
- 任务卡沿用现有待办样式。
- 不要把任务卡嵌套成多层装饰卡片。
- 完成父子任务后的透明度、历史、取消和删除显示与普通待办一致。

### 12.3 业务刷新

保存或修改清单后必须刷新：

- 每日看板。
- 待办页面。
- Android Widget。
- 手机局域网 Web 页面。
- Windows/桌面 Web 页面。
- 云同步队列或数据快照。

## 13. 待办页面行为

- 待办页面放置同一个快速清单入口。
- 可以查看所有未完成清单和其中的任务。
- 可以展开/收缩清单。
- 普通待办和清单任务使用相同的完成、取消、删除、历史和详情逻辑。
- 清单组标题不作为一条待办参与筛选、提醒或历史记录。
- 清单任务可以从普通详情页面打开，并且详情页必须知道其所属清单和父任务关系。
- 快速清单任务不应因为进入待办页面而绑定到当前规划文档日期。

## 14. 规划台衔接

本功能与规划台有层级能力上的联系，但不能恢复规划台已经被用户明确放弃的旧语法。

要求：

- 快速清单解析器是清晰、独立、可测试的输入协议。
- 不重新引入以 `#` 开头的标题或旧规划语法。
- `--#` 只表示清单中的可见说明。
- 快速清单保存后可以选择性生成/关联规划节点，但不能让保存依赖具体日期规划文档。
- 当前打开的是 5 月 20 日规划文档时，输入清单中的标题和任务不能自动被错误地塞到 5 月 20 日规划文档。
- 不要因为使用了 `PlanningNode` 的代码而恢复“按当前文档日期入库”的错误行为。
- 如果实现复用规划树代码，必须增加清单来源/独立容器边界。

## 16. 备份、迁移与云同步

### 16.1 备份

快速清单必须纳入现有 `.paykibak` 或项目统一备份格式：

- 清单标题。
- 清单 ID。
- 清单折叠状态。
- 任务 ID。
- 父子关系。
- 层级和排序。
- 任务标题。
- 任务说明/备注。
- 完成、取消、删除状态。
- 创建和更新时间。
- 与正式 TodoItem 的关联。

旧备份没有这些字段时，按空清单处理，不得导入失败。

导出后再导入必须保持：

- 层级不变。
- 同级顺序不变。
- 说明不丢失。
- 父任务完成联动仍然有效。
- 不产生孤儿节点。

### 16.2 Debug 到 Release

Debug 版本导出的数据应能被 Release 版本导入，且清单结构不丢失。不要把 Debug 签名、服务器密钥或 API Key 放进数据包。

### 16.3 云端同步

- 云端继续保存项目既有的加密快照，不新增明文任务存储。
- 清单父子关系、排序、折叠状态、说明、完成和取消状态必须进入加密快照。
- 同一个账号在手机、电脑和其他设备登录后看到相同层级。
- 同步必须使用稳定 ID、版本号和现有冲突解决机制。
- 不能只按标题去重或覆盖。
- 本地数据仍是设备可用的基础，服务器不可用时清单仍能正常查看和操作。
- 网络恢复后按照现有同步策略上传变化。

## 17. 测试要求

### 17.1 解析器单元测试

3. 一级、二级、三级和更深层级。

9. 空行和纯注释行。
10. 缺少标题。
11. 空任务。
12. 孤立说明。
13. 标题后的非法普通行。
14. 层级跳跃及警告/错误策略。
15. `//` 后内容不出现在保存结果。
16. 任务正文中数字序号不影响层级。
17. 重复提交的指纹行为。

### 17.2 Enter 行为测试

至少覆盖：

- `- task` 回车生成 `- `。
- `-- task` 回车生成 `-- `。
- `--# note` 回车生成 `-- `。
- 手动增减层级后下一次回车使用当前层级。
- Android IME 不重复插入换行。
- Web 键盘和粘贴多行内容与 Android 解析结果一致。
- 光标位置正确。

### 17.3 数据库与业务测试

至少覆盖：

- 保存清单原子性。
- 中途失败时无半个清单。
- 清单标题不进入历史。
- 每条任务都存在正式 TodoItem 或明确的稳定关联。
- 所有子任务完成后父任务递归完成。
- 子任务取消不被错误计为完成。
- 父任务取消整棵子树时状态一致。
- 删除不进历史。
- 取消进入历史并标记“已取消”。
- 删除任务后无孤儿节点。
- 重启应用后展开状态、排序和层级不变。

### 17.4 备份与同步测试

- 旧数据库 migration 不丢数据。
- 旧备份可导入。
- 新备份导出/导入不丢层级、备注、状态。
- Debug 导出后 Release 导入结构一致。
- 两台设备同步后清单一致。
- 服务器不可用时本地仍可用。
- 同步恢复后变化不会重复创建。

### 17.5 管理后台时间测试

- 服务端 UTC、浏览器 `Asia/Shanghai`：显示北京时间。
- 服务端 UTC、浏览器其他时区：显示浏览器时间。
- 所有时间字段使用统一脚本。
- 空时间显示 `-`。
- 自动刷新后仍正确。
- 时间戳异常不导致页面脚本崩溃。
- 用户数据 HTML 转义有效。
- JavaScript 禁用时不显示伪装成北京时间的服务器本地时间。

### 17.6 UI 验收

- Android 窄屏竖屏。

- 桌面宽窗口。
- 桌面窄窗口。

## 18. 禁止行为与非目标

本轮明确不做：

- 不恢复旧的 `#` 开头规划语法。
- 不把快速清单自动关联到当前规划文档日期。
- 不把标题行创建成待办。
- 不把所有任务存成一条长备注。
- 不自动创建 DDL、提醒或日程。
- 不把取消实现成删除。
- 不把删除写入历史。
- 不把清单标题写入待办历史。
- 不让 UI 勾选状态脱离 Repository 和数据库。
- 不新增明文云端任务存储。
- 不提交管理员密码、服务器密码、密钥、Token、API Key、真实 Base URL 或私人域名文件。

- 不只修改服务器系统时区来假装完成浏览器时区支持。

- 不在未测试的情况下宣称 Android、Web、Windows、Widget 全部完成。

## 21. 交付前示例验收

使用以下文本进行端到端测试：

```text
0913待办 //标题行
- 准备浙大的资料
-- 1. 身份证复印件
-- 2. 个人简历
-- 3. 成绩排名
--# 成绩排名是本学年的
- 取快递（取件码114514）
```

必须得到：

- 一个标题为 `0913待办` 的清单组。
- 五条真实任务：两个一级任务、三个二级任务。
- `1. 身份证复印件`、`2. 个人简历`、`3. 成绩排名` 都挂在 `准备浙大的资料` 下。
- `成绩排名是本学年的` 显示在 `3. 成绩排名` 下方，并保存为该任务说明。
- `//标题行` 不出现在任何任务标题、说明、预览、数据库、同步或历史中。
- 标题 `0913待办` 不作为待办，不进入历史。
- 新建任务无 DDL、无提醒，进入今日待办。
- 勾选三个二级任务后，`准备浙大的资料` 自动完成。
- 取消一个任务后，该任务进入已取消历史，不是删除。
- 删除一个任务后，该任务不进入历史。
- 重新打开应用、打开 Web、登录另一设备、导出再导入后，层级和说明仍然正确。

只有上述行为和各章节测试都满足后，才可以把版本标记为 `1.16.16`。
