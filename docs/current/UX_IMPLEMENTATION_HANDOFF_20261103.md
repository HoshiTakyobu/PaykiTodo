### 2.1 已明确要求与推荐补充规则

明确要求：上述 10 项；R3 的标题上限为 3 行；R5、R6 明确覆盖两端；R7 不能通过强行换掉用户选择的字体来冒充解决；本对话当前轮次只交付文档。

以下是为使任务可执行而提出的推荐默认值，不冒称用户逐项确认：

1. R10 覆盖双端每日看板；R2/R3/R4/R8/R9 以用户截图中的原生 Windows 客户端为主。Android 已满足的部分做针对性检查。LAN 网页保持兼容；只在共享数据契约受到影响时同步调整，不将此次扩展成三端全面重写。
2. R10 的排序理解为：日程使用开始时间，待办使用自己的 DDL。日程持续期间的待办仍按自身时间排在对应位置；不把待办 DDL 改成日程开始时间，不把任务自动隶属于日程。例：日程 14:00–17:00、待办 15:00，显示日程在前、待办在后。
3. 全天事项在同一卡片的“全天”行区；无 DDL 待办在“未定时间”行区，默认放有时刻事项之后。仍需处理的逾期待办保留日期与状态，按真实时间排，不因合并消失。
4. 同一排序时刻先日程后待办，再按稳定标识排序。父子任务的树结构在“待办”页保留；看板按独立事项时间排序，用轻量来源文字保留上下文，不为了把父子排在一起破坏时间顺序。
5. 保留看板“明天”预览，建议也按同一规则纳入明天有 DDL 的待办；不把无 DDL 事项重复放入明天。看板统一标题建议为“今日安排”。
6. R4 继续默认现代样式并保留用户已有选择。手机的 `desktopCalendarEventStyle` 目前主要承担传输保留，不能据此声称手机已经有双样式入口。
7. R3 对确实没有物理空间的短日程使用明确紧凑规则，详细内容由点击详情/悬浮补全；3 小时且有足够高度的卡片必须显示三行标题、时间、地点，不得继续降级成单行。

实施模型可直接按这些默认值推进，若收到用户新说明则更新对应规则。不要自行扩展成自动排程、任务时间改写、开机自启、窗口框架迁移或新同步协议。

## 4. R1：关闭主窗口后保留后台与托盘

### 目标行为

- 主窗口右上角 X、Alt+F4、系统菜单“关闭”隐藏主窗口，任务栏窗口入口消失，通知区域 PaykiTodo 图标仍在。
- 托盘双击与菜单“打开 PaykiTodo”恢复同一窗口，激活并尽量还原隐藏前的正常/最大化状态；窗口不能丢在已断开的显示器外。
- “最小化”仍按通常窗口最小化行为处理，除非用户另行要求最小化也进托盘。
- 托盘“退出”真正退出，停止提醒/同步计时器并释放图标。应用的次级编辑窗口仍正常关闭/取消。
- 主窗口隐藏时，本机提醒、已有后台同步和更新准备继续按现有规则工作。关闭窗口不等同退出账号；真正退出/关机后不保证桌面提醒。

### 已确认原因与入口

- `desktop/PaykiTodo.Desktop/Program.cs:24` 用 `app.Run(new NativeWindow(...))` 管理主窗口。
- `NativeWindow.cs:82` 的 `Closed` 处理器取消更新、停止计时器、释放 `DesktopReminders`。
- `DesktopReminders.cs:79–88` 已创建 NotifyIcon、双击/打开菜单；“退出”当前仅调用 `owner.Close()`。
- `desktop/PaykiTodo.Launcher/Program.cs` 已有更新目录相关 Mutex，并等待子进程退出，不能让关闭即隐藏破坏启动器的退出/更新流程。

### 实施步骤

1. 梳理主窗口、托盘、提醒服务的所有者。推荐将应用级托盘和显式退出入口从提醒职责中分离，或者在现有类中明确注入 `RestoreMainWindow` / `RequestExit` 回调；只保留一个图标。
2. 建立清楚的“隐藏”和“真正退出”状态。主窗口 `Closing` 对普通关闭取消销毁并隐藏；显式退出、系统注销/关机、受控测试清理走真实结束，不循环拦截。
3. 统一所有恢复入口，保留页面、选中日期、滚动位置、窗口状态。恢复提醒详情前先确保主窗口可见，避免详情藏在后台。
4. 真正退出的清理集中执行一次。防止异步同步/更新回调在退出后重新打开窗口；必要时停止新工作并允许既有原子保存完成。
5. 检查隐藏/重新显示是否触发重复初始化；`Loaded` 中的提醒、更新检查应具备一次性生命周期约束。
6. 保持启动器单实例规则。再次运行快捷方式至少不能产生重复主窗口或重复提醒；“从第二次启动唤醒窗口”可作为后续改进，不是此次硬性新增功能。
7. 在帮助中写明“关闭到托盘、托盘退出才结束”；用户找不到图标时提示它可能在 Windows 通知区域折叠菜单中。

验收重点：关闭后仍能提醒和同步；连续隐藏/恢复不增殖图标；显式退出和系统会话结束真的可退出；准备好的更新在真正退出再启动后仍能应用。见 A1。

## 6. R3：日程标题最多三行，显示时间与地点

### 已确认原因与入口

`NativeWindow.Calendar.cs:217–235`：`eventTitle.TextWrapping = NoWrap` 与 `CharacterEllipsis` 造成单行；正文只在高度满足条件时增加时间，地点只进入 ToolTip。`CalendarEventLayout.cs` 负责重叠分列，`NativeWindow.CalendarDrag.cs` 负责拖动。

### 显示契约

正常空间下顺序为：标题（1–3 行）→ 时间（1 行）→ 地点（有值时 1 行）。不要空地点占位，不把地点塞进标题，也不把三个字段合成一行。

例如宽度约为截图单日列、时长 14:00–17:00 时：

```text
【研究】小组会：阶段进度
汇报与实验结果讨论，确认
下一阶段安排及负责人…
14:00–17:00
实验楼 A 座 501
```

只有标题超过三行或遇到真实空间不足才出现省略；不足三行时不强行撑出空行。地点超长可省略，详情保留完整信息。

### 实施步骤

1. 提取时间轴日程正文构造逻辑，在最终卡片宽度及所选字体/字号下计算可用空间。重叠分列和窗口缩放后重新布局。
2. 先为时间、非空地点和上下内边距计算高度，再给标题分配最多三行。WPF `TextBlock` 没有可直接照抄的 `MaxLines` 属性；使用实际行高/文本度量与约束实现，不写不会生效的属性。
3. 去掉强制 `NoWrap`，对连续英文、数字和中文长标题同时检查换行及第三行省略。
4. 不能为容纳文字改变日程真实时间或把整个卡片随意拉高覆盖相邻时段。短卡片优先保证可读标题；能放下时增加时间、地点，完整三字段进入 tooltip、可访问说明和点击详情。
5. 基于高度形成一致的紧凑规则，记录边界样例：15/30 分钟、1/3 小时、重叠两列、较大字号。不能把紧凑规则用于截图中有大量空白的长日程。
6. R4 两种样式共用同一正文组件；月/全天小条受几何限制允许紧凑显示，列表/详情有空间应显示完整字段，标题同样不超过三行后省略。
7. 保留拖动、缩放、点击详情、过期淡化、当前时间线和独立日历显隐。文字控件不能阻断原来的命中区域。

验收重点：用相同标题与原图尺寸对比；三小时卡片显示三行标题、时间、地点；短日程不溢出其他时间块。见 A3。

## 10. R7：字体显示质量调查与修复

### 对用户问题的准确理解

用户投诉的是实际阅读质量：细笔画看似损失、边缘不平整或局部裁切，希望保留方正小标宋同时得到可靠显示。单张截图不能区分系统缩放、字体自身小字号表现、字体回退、抗锯齿、截图缩放与控件裁切。

### 已知事实

- `NativeWindow.cs:54` 和 `NativeUi.Dialog()` 已开 `UseLayoutRounding` / `SnapsToDevicePixels`。
- `NativeUi.ConfigureRendering():227` 已设 `TextFormattingMode.Display`、`TextRenderingMode.Auto`、`TextHintingMode.Fixed`。
- csproj 声明 `ApplicationHighDpiMode=PerMonitorV2`，但自定义 `app.manifest` 未显式写 DPI awareness。程序先调用 WinForms `ApplicationConfiguration.Initialize()` 再运行 WPF。仅凭 manifest 缺字段不能判定实际进程不感知 DPI。
- `DesktopFonts.cs` 管理已安装字体、中文别名和 12–22 的字号范围；`NativeUi` 管理真实字重。品牌/导航/问候有独立受保护资产，不能拿它们的渲染方式推断正文全被转成图片。

### 必须按顺序调查

1. 在独立资料中选择与用户相同字体，记录显示名称、实际字体族/字形命中、字号、字重、回退字形、窗口 DPI、显示器缩放、截图物理像素。只记录排查所需元数据，不打包用户字体文件。
2. 取未经缩放的原始截图，按 1:1 检查。对比方正小标宋与系统默认正文，使用同一字符串和相同页面。固定样例至少含中文细笔画、`14:00–17:00`、数字、标点、中英文混排。
3. 查询运行进程/窗口的实际 DPI awareness 和 `VisualTreeHelper.GetDpi`，检查 100%/125%/150%/200% 与跨屏移动。对照构建后 manifest 与运行初始化；只在确认问题后修复 DPI 配置。
4. 检查祖先元素是否有非整数 ScaleTransform、BitmapCache、低分辨率位图放大、强制软件渲染、半透明父层或重复缩放；确认 DIP 到物理像素只转换一次。
5. 检查字体匹配、真实可用字重与 fallback。单字重中文字体不能施加 synthetic bold；中英文字形来自不同字体时记录差别，保留用户所选主体字体。
6. 针对同一最小样例比较 WPF `Auto/ClearType/Grayscale`、`Display/Ideal` 的实际效果。不要批量叠加渲染开关；透明/淡化/动画表面与实底表面可能需要不同处理。
7. 检查固定高度、LineHeight、Padding、文本度量、表头/时间轴/下拉弹窗等裁切问题。R3 多行标题尤其不能按另一种字体的行高截掉笔画。
8. 只修有证据的问题，记录“现象 → 定位证据 → 修改 → 同条件对比”。如果某字号主要受字体设计与物理分辨率限制，应说明可验证边界并给字号/可选字体建议，不能偷偷替换用户字体，也不能用高倍截图重采样冒充清晰度提升。

验收重点：原字体保留、无缺笔画式裁切、无非原生缩放导致的整体模糊；修复结论必须对应原始对比图和真实运行参数。见 A7。

## 11. R8：桌面日历列表按所选周展示与翻页

### 已确认原因与入口

`NativeWindow.Calendar.cs:65–108`：列表仅过滤结束日期不早于 selectedDay，未限制周末；`Move()` 只把“周”识别为多日，列表一次前进一天；列表标题也按单日显示。

Android 对照是 `CalendarPanel.kt:1047` 的 `CalendarAgendaView()`，使用 `startOfWeek`、七个日期和周范围标题。借鉴其周语义与空日结构，不复制可能存在的边界错误。

### 实施步骤

1. 提取列表的独立周范围：`weekStart = WeekStart(selectedDay, weekStartMode)`，`weekEndExclusive = weekStart + 7 days`。所选周可以是过去或未来；“今天/本周”才返回当前周。
2. 列表模式的上/下翻页固定 ±7 个日历日，不受窗口宽度影响；周网格在窄屏原有 3 天导航逻辑保持各自语义。
3. 工具栏显示完整周范围，并为按钮提供“上一周/下一周”可访问名称。小月历高亮、点击日期、周/列表互切与范围标题保持一致。
4. 按当前显示时区做区间重叠过滤：`eventStart < weekEnd && eventEnd > weekStart`，时间段采用左闭右开。全天事件按其日历日期语义处理，不能机械减固定毫秒模拟本地日历日。
5. 保留跨天/跨周日程与各天的正确归属；跨日项按每天分段展示时，每段只在该天出现一次，标明延续且仍指向同一事件。边界上恰好于周一 00:00 结束的事件不能误入新周。
6. 列出七天的日期标题和当日事项，按全天优先、随后开始时间排序；空日轻量显示“本日暂无日程”，空周显示“本周暂无日程”。继续过滤取消/不可见/无权限事项。
7. 不能把看板“已结束不显示”的规则搬到周列表；用户查看过去一周时应能查看未取消的历史日程。明确完成的日程是否存在及其现行显示语义需按数据模型核实，不把全部历史一刀切掉。
8. 显示标题、时间、地点，点击仍进入详情。纯查看和翻周不改事件时间、不写数据库、不触发无意义同步。

验收重点：2026-11-02 至 11-08、跨月跨年、周日起始、跨周区间、窄窗口翻七天。见 A8。
