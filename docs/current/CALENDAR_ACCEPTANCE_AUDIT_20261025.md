日期：2026-10-25。核验基线：`f7f1590`，Android `1.17.1 / versionCode 393`、Windows `1.17.1.0`、Room `33`。本轮接续中断的最终检查，核对源码、测试原始结果、真实控件截图、数据保留及现有成品，没有修改产品行为或重建安装包。

## 后续验收结论

原 1.17.1 审计列明的核心日历与账号改进已实现，但当时缺少生产双账号原生全流程证据。用户随后手动完成验证码和第二专用账号注册，[原生协作验收](NATIVE_COLLABORATION_ACCEPTANCE_20261025.md)在 1.17.2 上通过 Android/Windows 邀请、接受、参与回应、双向已有日程编辑和撤权，补齐该项缺口；Windows 打包 EXE 的已有全天日程编辑入口也已实际验证。

该流程发现搜索权限、关闭提醒的规则显示和全天搜索日期问题，已在 [1.17.3](VALIDATION_1.17.3.md) 修复并通过新版只读访问及打开搜索时撤权复验。当前本地安装包为 1.17.3/395；下文测试计数和成品数据仍是 1.17.1 的历史审计。OEM、Windows 物理输入以及更广的协作能力边界仍保留，不能推定全部平台和所有组合均已验收。

## 仍未覆盖的能力与验证

- 参与者必须先成为共享日历已接受成员；组织者按现有服务契约固定为日历所有者。尚未实现任意外部参与者、独立日程组织者转移等更完整的协作模型。
- 已有单条日程 `BUSY/FREE` 字段和受限成员的忙闲投影；源码及服务路由未提供跨成员可用时段查询、排期建议的完整工作流。不能把一个忙闲选项当成忙闲排期功能。
- 当前共享日历通过账号邀请与成员权限访问；未发现独立订阅源管理或完整日历订阅工作流。会议室资源预约、冲突审批和视频会议创建/撤销服务也未形成实现链路。
- Windows 物理输入全流程和手机 OEM 场景仍缺完整直接证据。指定生产双账号原生协作已有后续证据，不再列为整体待验项；其他权限、离线和多设备组合没有全部覆盖。
- 上述扩展功能描述当前能力边界，不表示本次复核已新增开发范围或完成这些能力。
